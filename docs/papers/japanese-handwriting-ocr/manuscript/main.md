# 研究目的

Learnit では、撮影したノートの認識結果を利用者が読み直し、必要な語句や文を Anki カードにする。文字の誤りに加え、列の順序が入れ替わったり行が抜けたりすると、元画像に戻って文章を組み立て直す必要がある。本研究の主指標は文字編集の量とし、縦書き、横書き、媒体、応答時間を併記する。編集操作数や修正時間の測定は別の実験とする。

# データと方法

## 書き手による分割

JaWildText の手書きサブセットを配布リビジョン `627ca7e…` に固定した。元データは51人の1,065枚と6,002行の人手転記を含む。紙、タブレット、ホワイトボード上に書き写した現代の日本語が中心である。Parquet 6ファイルの SHA-256 を照合した。 [@maeda2026; @llmjp2026]

配布上の画像 ID は2組で衝突し、どちらの組もファイル名を使うと別画像として区別できた。ファイル名全体からケース ID を作り、配布上の ID も保存した。画像バイト列と RGB 画素の完全一致は0組だった。30文字以上の同一転記、または知覚ハッシュの距離が5以下かつ転記の正規化編集類似度が0.85以上のページを関連候補とした。同一書き手で転記が一致する1組が検出された。書き手と関連画像の連結成分を分割の単位とした。

開発用には既出の7人を含めた。固定シードで上限1,000枚に収めると、開発211枚、最終評価789枚、対象外65枚となった（図\ref{fig:cohorts}）。開発用から縦横と媒体を含む100枚をパイロットに選んだ。最終評価の39人は開発側と重複しない。100枚のパイロットはホワイトボード40枚、タブレット35枚が多い。最終評価の紙は690枚で、パイロットの結果を本番に外挿しない。

## 正解と入力画像

上流は行ポリゴンの過半数が縦長かを判定し、横書きは重心の上から下、縦書きは右から左へ並べる。パイロットでは44枚、最終評価では268枚について、Codex が認識出力を参照せず、ポリゴンと画像を目視照合した。全縦書き、縦横の混在や方向情報の不一致、短い欄外表記を含む候補と、残りの横書きから媒体別に抽出したページが対象だった。確定した行の配列と理由は監査記録に保存した。独立した人による再監査は未実施。 [@llmjpcode2026]

本測定用の画像は EXIF の向きを適用し、RGB に変換する。長辺を2,200ピクセル以下に収め、品質92の JPEG を一度生成し、両者で同じファイルを使う。入力と転記のハッシュ、除外理由、データ・コードの版を記録した。Apple はアプリと同じ `ImageOCR.readOnMac` を呼ぶ。Google は既存の `GoogleVisionTranscriber` を使い、`DOCUMENT_TEXT_DETECTION` と日本語ヒントを指定する。初期化の確認は採点対象外の画像で行う。タイムアウトや一時的な HTTP エラーだけを最大1回再試行し、各試行の状態と所要時間を保持する。 [@applevision; @googlevision]

## 評価指標と判断基準

正解と出力は Unicode NFC に正規化し、空白を除く。句読点・文字種は維持する。ページ $i$ の正解文字数を $n_i$、挿入・削除・置換の最小合計を $d_i$ とすると、主指標は $\mathrm{CER}_{\mathrm{micro}} = \sum_i d_i / \sum_i n_i$ となる。動作確認に成功したランで発生する空出力や最終エラーは全削除で数える。重大失敗は空出力、最終エラー、または $d_i \geq n_i$ と定義する。

同じページの Google と Apple の差は、書き手・文書グループを10,000回再抽出して95%信頼区間を求める。文字誤り率が3ポイント以上改善し、重大失敗率の悪化が1ポイント以内と判断するには、改善の信頼区間の下限と悪化の信頼区間の上限がそれぞれ基準を満たすことを求める。完全一致、p50・p95の待ち時間、方向と媒体ごとの分母も報告する。事前試験の初回時間は単発値である。

# 実測結果

通常の macOS 27.0 Terminal で、両者に公開の縦書き画像1枚（配布ファイル番号0004、2,714 × 5,000ピクセル）を与えた。この書き手は対象外のグループに属する。入力は配布ビューアーの JPEG で、本測定用の長辺2,200ピクセルの画像とは別のハッシュを持つ。

| 経路 | 文字を返した枚数 | 所要時間 | 編集数 / 正解文字 | CER |
|:-----|-----------------:|---------:|-------------------:|----:|
| Apple Vision | 0 / 1 | 29.43秒 | — | — |
| Google Cloud Vision | 1 / 1 | 1.50秒 | 48 / 117 | 41.0% |

Table: 通常の Terminal での事前試験。Apple の初期化診断が出たため対応差は算出できない。

Google は正解の6行に対し19の非空行を返した。最小編集列は挿入21、削除18、置換9だった。Apple はモデルバンドルの診断を出して空文字列を返した。制限付きプロセスでは Apple のモデルキャッシュへのアクセスと Google の認証時の通信も失敗した。初期化障害のある Apple の出力は、精度評価の分母に入れなかった。パイロット100枚と最終評価789枚について、集計できる完了ランはまだない。

# 代表的な失敗と限界

事前試験では Google が縦書きの文字を返したものの、冒頭の断片が離れた行に分かれ、正解にない文字列が挿入された。文字の抽出と読む順序の復元を区別して調べる動機になる。1枚のエラーを基に、縦書きや他の媒体におけるエンジンの性能は一般化できない。

参照生成側でも、横書き画像0443では用紙の罫線番号が文を分断した（図\ref{fig:order}）。縦書き画像0304では本文に三辺の番号が混ざった。これらの番号は配布された転記に含まれるため、本文の後にまとめた。曖昧なページの読み順には規約が必要であり、14枚の修正はモデル精度と独立した参照整備の結果である。同じ文章の書き換えや一部だけが写った重複画像は、この重複検出で残り得る。

# Learnit への設計提案

**既定値。** 現段階では既定の認識経路を切り替える根拠がない。同じ公開画像で初期化に成功する macOS を確保し、設定を固定してパイロットを実行する。Google 側が先に完了した場合は、その経路の絶対精度と待ち時間を報告する。

**再認識。** 最初に比較する候補は、初回の出力が空、または利用者が不十分と判断した場合に、同じ切り抜きを Google で再認識できる操作である。修正中の下書きを保持し、再認識結果を反映するか選べるようにする。実験では追加アップロード数、重大失敗率、文字編集量を測る。

**撮影ガイドと前処理。** 罫線の数字や欄外が入ると読み順の判断が難しい。先に手動の切り抜きと回転を案内し、パイロットで誤りが集中したときだけ前処理候補を一つ選ぶ。自動切り抜きや拡大の効果は確認用データで比較する。CER とカード修正時間の関係は、利用者による別の実験で確かめる。
